## Finding: Codex runs plugin hooks only in the compatibility layout

The plan (O1) asks for the portable format: a root `plugin.json` with `extensions.com.openai.hooks`. With that layout Codex loads the skills and the MCP server but **never runs the plugin's hooks**. Each variant was tested with `codex exec --dangerously-bypass-hook-trust` and a `SessionStart` probe hook that appends `$PLUGIN_ROOT`, `$PLUGIN_DATA` and a shell variable to a file:

| Plugin layout | Codex 0.169.0 | Codex 0.171.0-alpha.5 |
|---|---|---|
| Root `plugin.json` with `extensions.com.openai.hooks` | hooks do not run | hooks do not run |
| Root `plugin.json`, no `hooks` key (default `hooks/hooks.json` discovery) | hooks do not run | not tested |
| Root `plugin.json` without `com.openai`, plus a `.codex-plugin/plugin.json` overlay with `hooks` | hooks do not run | not tested |
| Root `plugin.json` plus a `.claude-plugin/plugin.json` | hooks do not run | not tested |
| **Only `.codex-plugin/plugin.json`** (Codex compatibility layout) | **hooks run** | **hooks run** (full smoke, below) |
| Claude Code layout (`.claude-plugin/plugin.json`, `hooks/hooks.json`) | hooks run | not tested |
| User-level `$CODEX_HOME/hooks.json` (control) | hooks run | not tested |

The app-server `hooks/list` call (no thread) also lists the user-level hook but no plugin hook, whatever the layout.

With the orchestrator's go, `plugins/codex/rushdb` uses the compatibility layout: `.codex-plugin/plugin.json` (with `skills`, `mcpServers: ./.mcp.json`, `hooks`, `interface` and `extensions.com.openai.onboardingSkill`) and `.mcp.json`. The OpenAI directory ZIP has no hooks and stays portable. `scripts/check-codex.ts` fails if a portable `plugin.json` or `mcp.json` appears in the Codex folder. The CI `codex` job runs `scripts/smoke/codex.sh` on 0.169.0 (blocking) and on the latest release (not blocking), so a Codex release that changes this shows up. The plugin can then move to the portable layout.

A negative control confirms the smoke catches this. In a copy of the repo with a portable `plugin.json` and `mcp.json` added to the Codex folder, `scripts/smoke/codex.sh` fails with "plugin hooks did not fire: no RushDB request".

### Other Codex facts verified

- **Marketplace precedence.** With both files present, Codex reads `.agents/plugins/marketplace.json` (`codex plugin list` prints that path, and the entry resolves to `plugins/codex/rushdb`). Without it, Codex falls back to `.claude-plugin/marketplace.json`. `codex plugin marketplace add rush-db/agent-plugins` against today's `main` installed `plugins/claude/rushdb`. Documented in the README.
- **Environment reaches plugin hooks.** A variable exported in the shell that starts `codex exec` reached the hook, and so did `PLUGIN_ROOT` (the installed cache folder) and `PLUGIN_DATA` (`$CODEX_HOME/plugins/data/rushdb-rushdb`). This closes R-OAI open question 1 for `codex exec`. The TUI and desktop app were not tested.
- **Install.** `codex plugin marketplace add ./` then `codex plugin add rushdb@rushdb` installs into `$CODEX_HOME/plugins/cache/rushdb/rushdb/0.1.0/`. `codex mcp list` shows `rushdb  https://mcp.rushdb.com/mcp  enabled  Not logged in`. `codex debug prompt-input` lists all five skills, including `rushdb-setup`.
- **Hosted MCP at session start.** With the plugin enabled, every `codex exec` session connects to `https://mcp.rushdb.com/mcp`, and so does `codex mcp list`. Before sign-in this gives the expected 401 (`AuthRequired … No token provided`). This matches the README's "What leaves your machine".
- **The smoke test never contacts production.**
  - `scripts/smoke/codex.sh` writes `[plugins."rushdb@rushdb".mcp_servers.rushdb] enabled = false` into the scratch `config.toml` before `codex mcp list`. The plugin's own `.mcp.json` is unchanged, and `codex mcp list` shows the server as `disabled`. The key `plugins."rushdb".mcp_servers.rushdb` from the OpenAI docs had no effect in 0.169.0.
  - Codex runs with `HTTPS_PROXY` and `HTTP_PROXY` set to the fake services, which log every outside `CONNECT` and refuse it. Codex honors the proxy: a probe run with the server still enabled logged `CONNECT mcp.rushdb.com:443` (refused, so no connection was made).
  - In the final runs, plain and `--engine` on 0.169.0, the proxy saw only Codex's own `ab.chatgpt.com`, `chatgpt.com`, `api.github.com` and `github.com`, all refused, and **no connection attempt to any `rushdb.com` host**. The script fails if one appears, and also if no request went through the proxy at all.

### Deviation from the plan: `UserPromptSubmit` and `Stop` are synchronous

The plan (O1) has both hooks `async`. Codex cancels unfinished background hooks when a session ends, so `codex exec` and a quick quit would lose the last turn. This is the same reason the Claude `Stop` hook is synchronous (f8587bb). With the orchestrator's go, both run synchronously with `timeout: 5`. They only write local files (`prompts/`, `sessions/`, `outbox/`) and spawn a detached flush, which does the network work after the hook has returned.

Per-turn cost: each `hooks.json` command was run through `sh -c` with real Codex payloads and `recall+persist`. The times include Node start-up, which is what Codex waits for.

| Hook | API answering (n) | API hanging (n) |
|---|---|---|
| `UserPromptSubmit` | median 67 ms, max 86 ms (10) | median 71 ms, max 91 ms (10) |
| `Stop` | median 75 ms, max 83 ms (10) | median 76 ms, max 91 ms (10) |
| `SessionEnd` (outbox pending) | median 68 ms, max 87 ms (5) | median 86 ms, max 89 ms (5) |
| `SessionStart` recall | median 85 ms (3) | 1,572 ms (3): the 1.5 s recall timeout |

So a turn costs about 150 ms in total with automatic context on, whether or not RushDB answers. `SessionEnd` stays well inside its 1 s Codex budget (`timeout: 1`).

### Other choices

- The `SessionStart` matcher is `startup|resume|compact`, as the plan says, with `additionalContextLimit: 4000`. There's no `PostCompact` hook, because Codex passes no compaction summary to it.
- The onboarding skill `rushdb-setup` signs the MCP tools in (`codex mcp login rushdb`), explains the switch, and gives the user the commands to create `~/.config/rushdb/config.json` themselves with mode 0600. The model is told never to ask for, read, write or print a key. It may only check that the file exists and see its mode with `ls -l`.
- The marketplace entry uses `policy.authentication: ON_INSTALL`. The first-use token is still unverified (R-OAI open question 7), and `check-codex` accepts `ON_INSTALL` or `ON_USE`.
